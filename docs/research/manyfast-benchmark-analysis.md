## 실제 제품 프로세스

```text
아이디어 또는 파일
  → 구조화 질문
  → PRD 점진 생성
  → PRD 검토
  → 기능 계층 생성
  → 기능 상세 검토
  → 유저플로우 생성
  → 화면 선택
  → 와이어프레임 생성·편집
```

이 흐름의 핵심은 각 산출물이 독립된 결과물이 아니라 다음 산출물의 입력이라는 점이다. 질문의 답은 PRD가 되고, PRD는 요구사항과 기능의 계층이 되며, 기능은 흐름과 화면으로 이어진다.

## 화면 디자인 분석

### 1. 고정된 작업 프레임

프로젝트명과 산출물 탭을 상단에 고정하고, 왼쪽은 AI 대화, 중앙은 주 작업 영역, 오른쪽은 선택 항목의 정보 또는 목록으로 사용한다. 작업 종류가 바뀌어도 공간의 역할이 크게 변하지 않아 사용자가 위치를 다시 학습할 필요가 적다.

### 2. 문서가 주인공인 시각적 위계

색상은 흰색과 연한 회색을 넓게 사용하고 보라색을 선택, 생성, 주요 CTA에 제한한다. 장식보다 문서 내용과 노드 연결이 먼저 보인다. 작은 글자와 낮은 대비는 대형 캔버스에서 정보 밀도를 높이지만, 가독성과 접근성은 별도로 보완할 필요가 있다.

### 3. 빈 상태가 다음 행동을 설명

PRD, 유저플로우, 와이어프레임의 빈 화면에는 결과가 나타날 위치와 생성 조건, 시작 버튼이 함께 표시된다. 빈 상태가 안내 문구 이상의 온보딩 역할을 한다.

### 4. 점진적 공개

처음부터 모든 편집기를 보여주지 않는다. 질문을 완료하면 PRD, PRD가 준비되면 기능명세서, 플로우가 준비되면 와이어프레임을 제안한다. 다음 단계의 진입 조건을 화면에서 자연스럽게 설명한다.

### 5. 개요와 상세의 분리

중앙 캔버스는 전체 구조를 보고, 우측 패널은 선택한 한 항목을 검토하는 데 사용한다. 전체 맥락을 잃지 않으면서 세부 정책을 다룰 수 있는 구조다.

| PRD | 별도 페이지의 긴 입력 폼에서 재작성 | 대화 답변으로 생성하고 같은 화면에서 검토 | PRD 입력 폼을 없애고 대화·직접 편집·부분 보완으로 통합하는 편이 낫다. |
| 수정 | 영역의 결정을 지우고 다시 질문 | 기존 문맥을 유지하며 선택 항목을 수정 | 항목 단위 수정과 변경 제안 승인 구조가 필요하다. |
| 참고 자료 | PRD 단계에서 파일 업로드 | 프로젝트 시작과 채팅에서 자료 첨부 | 자료 첨부를 설계 시작부터 사용할 수 있어야 한다. |
| 화면 연결 | `/survey`와 `/prd`가 분리 | 동일 프로젝트 셸에서 탭 전환 | 하나의 Blueprint 작업 공간 안에서 산출물을 전환해야 한다. |

## 리빌드 방향

### 제품 구조

리빌드의 중심 객체를 `설문 응답`에서 `Blueprint 프로젝트`로 바꾼다. 프로젝트 안에는 대화, 참고 자료, 확정된 설계 항목, 변경 제안, 요구사항명세서, PRD가 함께 존재한다.

```text
Blueprint Project
├─ Conversation
├─ Sources
├─ Product Definition
├─ Requirements
└─ Documents
   ├─ Requirements Specification
   ├─ PRD
   └─ Setup Guide
```

### 권장 화면 구조

```text
┌─────────────────────────────────────────────────────────────┐
│ 프로젝트명        설계 | 요구사항명세서 | PRD      내보내기 │
├──────────────────┬──────────────────────────┬───────────────┤
│ AI 대화          │ 현재 문서 또는 설계 구조 │ 검토·상세     │
│ 질문·답변        │                          │ 상태          │
│ 참고 자료        │ 항목 선택과 직접 편집    │ 근거          │
│ 작업 진행 상태   │ AI 변경안 표시           │ 수용 기준     │
│ 입력창           │                          │ 승인·거절     │
└──────────────────┴──────────────────────────┴───────────────┘
```

- 왼쪽 대화는 질문, 파일, 작업 상태를 담당한다.
- 중앙은 현재 선택한 설계 또는 문서를 편집한다.
- 오른쪽은 선택한 항목의 상태, 근거, 수용 기준과 AI 변경안을 검토한다.
- 모바일에서는 세 영역을 `대화`, `설계`, `검토` 탭으로 전환한다.

### 프로세스

1. 사용자가 아이디어를 입력하거나 자료를 첨부한다.
2. Agent가 한 답변에서 제품 목표, 사용자, 기능, 제약을 복수로 추출한다.
3. 추출 결과를 변경 제안으로 표시하고 사용자가 선택적으로 승인한다.
4. 승인된 설계가 중앙 작업 영역과 문서 초안에 바로 반영된다.
5. Agent는 남은 핵심 공백만 질문한다.
6. 사용자는 요구사항명세서와 PRD를 탭으로 오가며 직접 수정하거나 AI에 부분 보완을 요청한다.
7. 최종 검토에서 미정 사항, 충돌, 수용 기준 누락을 확인한다.
8. 요구사항명세서, PRD, 설정 가이드를 각각 또는 묶어서 내보낸다.

## 유지할 것과 바꿀 것

### 유지

- AI 제안을 사용자가 승인한 뒤 반영하는 원칙
- 비개발자가 답하기 쉬운 질문과 추천 선택지
- 요구사항명세서, PRD, 맞춤 설정 가이드 생성
- OpenAI 실패 시 입력과 확정 설계를 보존하는 동작
- Markdown 복사와 다운로드

### 재설계

- 고정 7단계 진행과 한 필드씩만 해석하는 API
- 확정 값만 나열하는 설계 보드
- PRD를 별도 폼에서 다시 입력하는 흐름
- 문서 전체를 매번 재생성하는 서비스 계약
- 대화와 산출물이 라우트 이동으로 분리되는 화면 구조

### 이번 범위에서 제외

- 유저플로우 캔버스
- 와이어프레임 생성·편집
- 실시간 공동 편집과 코멘트
- 결제·크레딧 체계
- Jira, GitHub, MCP 쓰기 연동

## requirements와 PRD에 반영할 핵심 결정

- Blueprint는 질문지가 아니라 프로젝트 단위의 AI 설계 작업 공간이다.
- PRD와 요구사항명세서는 같은 확정 설계 데이터를 사용한다.
- 대화는 설계를 생성할 뿐 아니라 기존 항목을 조회하고 부분 수정할 수 있다.
- Agent는 여러 변경안을 항목 단위로 제안하며 사용자는 개별 승인 또는 거절한다.
- 문서는 대화 종료 후 한 번 생성되는 결과가 아니라 설계와 함께 갱신되는 작업물이다.
- 기술 환경 질문은 제품 정의에 필요한 시점에 제시하고, 초기 흐름을 지배하지 않는다.
- 모든 최종 문서는 확정, 미정, 가정, 근거를 구분해 표시한다.
