# 대화·선택 프로세스 명세

이 문서의 제품 규칙을 실제 상태 전이, guard와 테스트 경로로 적용하는 기준은 [Blueprint 프로세스 설계](../process/README.md)를 따른다.

## 목적

이 문서는 Agent가 연속 질문을 선택하고, 답변을 폼으로 수집하며, 설계 제안을 누적하는 규칙을 정의한다. 대화의 목표는 질문을 모두 소진하는 것이 아니라 문서 작성에 필요한 결정을 신뢰할 수 있는 상태로 만드는 것이다.

## 기본 루프

```text
사용자 입력
  → 사실과 의도 추출
  → 설계 변경안 생성
  → 사용자 검토
  → 확정 설계 반영
  → 공백·충돌 분석
  → 다음 질문 선택
  → 문서 준비도 갱신
```

각 화살표가 AI 호출을 의미하지 않는다. 표준 선택 검증, proposal 승인, 공백 계산과 다음 질문 선택은 코드가 수행한다. 자유 답변 분석, 질문 표현, 설명과 추천만 작업별 AI task로 호출한다. 모델·token 정책은 [AI 오케스트레이션과 모델 정책](12-ai-orchestration-and-model-policy.md)을 따른다.

## 대화 AI 분기

| 사용자 사건 | AI task | 모델 profile | 응답 |
| --- | --- | --- | --- |
| 첫 아이디어·자유 답변 | `TURN_ANALYZE` | DEFAULT low | 설명, proposal 요약, 복수 proposal |
| 표준 선택 | 없음 | 없음 | 로컬 저장 후 다음 질문 판단 |
| 다음 질문 표시 | 기본은 없음, 필요 시 `QUESTION_COMPOSE` | LIGHT low | catalog 또는 맥락형 question block |
| 잘 모르겠어요 | 기본은 없음, 필요 시 `QUESTION_EXPLAIN` | LIGHT low | 정적/맥락형 explanation, 같은 질문 |
| 추천해 주세요 | `OPTION_RECOMMEND` | DEFAULT low | recommendation block + proposal |
| 나중에 결정/건너뛰기 | 선택적 또는 없음 | 없음 | deferred/skip 저장 |
| 오래된 대화 압축 | `CONTEXT_COMPACT` | LIGHT low | 출처 있는 구조화 summary |

한 task 응답은 여러 표시 block을 포함할 수 있다. block은 `assistant_text`, `question`, `explanation`, `recommendation`, `proposal_summary`, `conflict_notice`, `readiness_notice`, `next_action`만 허용하며 세부 계약은 [프롬프트·응답 계약](13-prompt-and-response-contracts.md)을 따른다.

## 대화 상태

| 상태 | 진입 조건 | 사용자에게 제공할 행동 | 종료 조건 |
| --- | --- | --- | --- |
| `intake` | 새 프로젝트 | 아이디어 입력, 파일 첨부, 예시 선택 | 분석 가능한 입력 확보 |
| `extracting` | 새 입력 수신 | 작업 중단 | 구조화 응답 검증 완료 |
| `proposal_review` | 변경안 존재 | 승인, 수정, 거절 | 모든 변경안 처리 |
| `discovering` | 필수 공백 존재 | 선택, 직접 입력, 건너뛰기 | 답변 제출 또는 명시적 미정 |
| `conflict_review` | 확정 항목과 충돌 | 기존 유지, 새 값 선택, 수정 | 충돌 해결 |
| `document_ready` | 준비 조건 충족 | 문서 생성, 질문 계속 | 사용자 선택 |
| `document_editing` | 요구사항명세서 또는 PRD 생성 완료 | 직접 편집, 부분 보완, 검토 | 준비 완료, 내보내기 또는 추가 대화 |
| `completed` | 최종 검토 완료 | 다운로드, 다시 열기 | 사용자가 작업 재개 가능 |
| `error` | 요청 또는 저장 실패 | 재시도, 입력 수정 | 성공 또는 취소 |

상태 전이는 클라이언트가 결정한다. Agent 응답은 다음 상태 후보를 제공할 수 있지만 스키마 검증과 현재 프로젝트 상태를 통과해야 한다.

## 설계 영역

질문 엔진은 다음 영역의 공백을 관리한다.

1. 제품 한 줄 정의
2. 해결할 문제와 배경
3. 제품 목표
4. 주요 사용자와 역할
5. 핵심 사용자 시나리오
6. 핵심 기능
7. 범위와 제외 범위
8. 기능별 동작과 수용 기준
9. 데이터와 외부 연동
10. 인증과 권한
11. 운영, 배포, 보안과 일정 제약
12. 성공 기준과 위험

기술 환경은 독립된 설문 단계가 아니라 관련 기능과 제약을 실현하기 위한 결정 영역으로 다룬다.

## 다음 질문 선택 규칙

### 후보 생성

질문 엔진은 다음 조건에 해당하는 질문만 후보로 만든다.

- 대상 설계 항목이 누락 또는 미정이다.
- 선행 조건이 충족되었다.
- 같은 의미의 질문이 현재 처리 중이지 않다.
- 사용자가 해당 질문을 명시적으로 건너뛴 후 재질문 조건이 발생하지 않았다.
- 확정 데이터만으로 답을 추론할 수 없다.

### 우선순위 계산

질문 후보는 아래 요소로 정렬한다.

| 요소 | 높은 점수를 받는 조건 |
| --- | --- |
| 문서 필수성 | 목표, 사용자, 핵심 기능 등 문서 생성 필수 항목 |
| 후속 영향 | 답변이 여러 질문 또는 문서 섹션을 활성화함 |
| 위험도 | 보안, 개인정보, 권한, 외부 연동과 관련됨 |
| 불확실성 | 서로 다른 제안이나 충돌이 존재함 |
| 사용자 맥락 | 직전 대화와 직접 관련됨 |
| 피로도 | 최근 유사 질문이 많으면 감점 |

동점이면 제품 문제와 사용자 정의를 기능·기술 질문보다 먼저 묻는다.

### 종료 판단

다음 조건을 모두 만족하면 `document_ready`를 제안한다.

- 제품 문제, 목표와 핵심 사용자가 확정됨
- 핵심 기능과 제외 범위가 확정됨
- 각 핵심 기능에 최소 한 개의 수용 기준이 존재함
- 데이터, 권한, 운영 제약이 확정 또는 명시적 미정임
- 성공 기준과 주요 위험이 작성됨
- 처리되지 않은 충돌이 없음

사용자는 준비 상태에서도 질문을 계속하거나 문서를 먼저 생성할 수 있다.

준비도는 숫자로 표시하지 않는다. 핵심 정보 누락 또는 처리되지 않은 충돌이 있으면 문서 생성을 막고, 명시적으로 미룬 항목은 오픈 이슈로 포함한 채 생성을 허용한다.

## 문서 생성 순서

1. 설계 준비 조건을 충족하면 코드로 Requirements plan을 만들고 DEFAULT(Mini) draft와 별도 review를 실행한다.
2. review issue가 자동 수정 가능하면 문제 section만 한 번 repair하고 다시 review한다.
3. 사용자가 요구사항명세서의 미정, 충돌과 핵심 수용 기준을 검토한다.
4. 요구사항명세서를 `ready`로 확정한다.
5. 같은 설계 revision을 기준으로 코드 plan, FINAL(Terra) PRD draft와 DEFAULT(Mini) review를 실행한다.
6. 요구사항명세서가 다시 `review_required`가 되면 새 PRD 생성과 갱신을 잠근다.

설정 가이드는 확정 기술 결정에 맞춰 Agent가 전체 내용을 생성하며 사용자 승인 전에는 초안이다.

## 선택 폼 생성 기준

Agent가 임의 UI를 생성하지 않는다. 질문 엔진이 결정 목적에 맞는 허용 폼과 기본 문구를 지정하며, catalog로 부족한 경우에만 Agent가 맥락형 표현을 작성한다.

| 답변 성격 | 폼 유형 | 사용 기준 |
| --- | --- | --- |
| 서로 배타적인 결정 | `single` | 배포 위치, 주요 실행 환경 |
| 동시에 여러 값 가능 | `multiple` | 사용자 역할, 알림 채널 |
| 표현 범위가 열려 있음 | `text` | 문제 정의, 제외 범위 |
| 수치가 필요함 | `number` | 사용자 수, 처리량 |
| 범위가 유용함 | `range` | 일정, 예산, 응답 시간 |
| 우선순위가 필요함 | `rank` | MVP 기능 순서 |
| 추출 결과 확인 | `confirm` | AI가 발견한 사용자·기능·제약 검토 |

### 선택지 수와 표현

- 2개: 버튼 또는 분할 선택
- 3~5개: 라디오 카드 또는 체크 카드
- 6~10개: 간결한 목록
- 10개 초과: 검색형 선택
- 설명 없이 이해하기 어려운 선택지에는 한 줄 설명을 포함한다.
- 선택지는 가능한 한 상호 배타적이고 같은 추상화 수준을 유지한다.
- 추천 항목에는 이유를 표시하지만 기본 선택 상태로 두지 않는다.

### 직접 입력과 불확실성

질문 정책은 필요에 따라 아래 행동을 허용한다.

- `직접 입력`: 표준 선택지에 없는 값을 추가한다.
- `잘 모르겠어요`: 개념 설명과 비교를 요청한다.
- `추천해 주세요`: 현재 확정 설계를 근거로 추천안을 생성한다.
- `나중에 결정`: 해당 항목을 명시적 미정으로 저장한다.
- `건너뛰기`: 선택적 질문을 답변 없이 종료한다.

추천안은 자동 확정하지 않고 일반 변경안과 동일하게 검토한다.

## 질문 응답 계약

```ts
interface QuestionSpec {
  id: string;
  topic: string;
  prompt: string;
  help?: string;
  answerMode: "single" | "multiple" | "text" | "number" | "range" | "rank" | "confirm";
  options?: QuestionOption[];
  allowCustomAnswer: boolean;
  allowUnknown: boolean;
  allowDefer: boolean;
  required: boolean;
  targetItemTypes: DesignItemType[];
}

interface QuestionOption {
  value: string;
  label: string;
  description?: string;
  recommended?: boolean;
  recommendationReason?: string;
}
```

표준화가 필요한 선택지는 질문 카탈로그의 `value`만 사용한다. 직접 입력은 원문을 보존하고 분류 결과를 별도 속성에 저장한다.

## 답변 분석 규칙

1. 사용자의 원문을 변경하지 않고 메시지로 보관한다.
2. 현재 질문과 직접 관련된 답을 우선 추출한다.
3. 같은 답변에 포함된 다른 명확한 사실도 별도 변경안으로 생성한다.
4. 사실, 선호, 가정과 Agent 추천을 구분한다.
5. 추론한 내용에는 추론임을 표시하고 자동 확정하지 않는다.
6. 기존 항목과 같은 의미이면 중복 제안을 만들지 않는다.
7. 기존 항목과 다른 의미이면 충돌 변경안을 만든다.
8. 값의 형식과 허용 범위를 검증한 후 사용자에게 표시한다.

## 변경안 검토

각 변경안 카드에는 다음을 표시한다.

- 추가, 수정 또는 삭제 유형
- 대상 설계 영역과 항목 이름
- 제안 내용
- 기존 내용이 있으면 전후 비교
- 제안 이유
- 사용자 답변 또는 첨부 자료 근거
- 관련 문서와 영향받는 항목

사용자는 개별 승인, 승인 전 수정, 거절을 수행한다. 현재 질문과 관련된 변경안을 모두 처리하기 전에는 다음 시스템 질문으로 이동하지 않는다. 자유 대화는 계속 작성할 수 있으며, 같은 대상을 바꾸는 새 변경안은 기존 변경안을 대체할지 먼저 확인한다.

## 조건부 질문 예시

```text
사용자별 데이터 필요
  → 인증 필요 여부
  → 인증 필요
     → 사용자 역할
     → 로그인 방식
     → 권한 차이

외부 알림 필요
  → 알림 이벤트
  → 알림 채널
  → 실패와 재시도 정책

파일 업로드 필요
  → 지원 파일 유형
  → 파일 크기
  → 보관 기간
  → 개인정보 포함 여부
```

선행 결정이 바뀌면 종속 결정을 삭제하지 않는다. `review_required` 상태로 바꾸고 사용자에게 영향을 설명한다.

## 대화 요약과 컨텍스트

- 프로젝트마다 하나의 연속 대화 스레드만 사용한다.
- 최근 메시지는 원문으로 전달한다.
- 오래된 대화는 확정 결정, 미정 사항, 거절된 방향과 근거로 요약한다.
- 현재 질문과 관련 없는 전체 문서를 반복 전송하지 않는다.
- 첨부 자료는 필요한 발췌와 파일 메타데이터만 전달한다.
- Agent가 참조한 항목 ID를 응답에 포함해 결과를 추적한다.
- 요청 전 task별 token budget을 계산하고 provider 자동 truncation을 사용하지 않는다.
- 오래된 대화 요약은 새 사실을 추가하지 않으며 source message ID를 보존한다.

## 실패 처리

- 네트워크 실패: 전송 전 입력을 보존하고 동일 요청을 재시도한다.
- 응답 스키마 실패: 프로젝트를 변경하지 않고 안전한 오류를 표시한다.
- 빈 제안: 추가 설명을 요청하거나 직접 입력 모드로 전환한다.
- 선택값 불일치: 표준 값으로 임의 변환하지 않고 사용자 확인을 요청한다.
- 중복 응답: 요청 ID로 중복 반영을 막는다.
- 취소: 진행 중 작업을 중단하고 완료된 저장 상태로 돌아간다.
- AI 요청 실패: 입력과 확정 설계를 유지하고 재시도를 제공하며 fallback 제안이나 문서를 만들지 않는다.

## 품질 점검 항목

- 질문은 한 문장에서 하나의 주요 결정을 요구하는가?
- 선택지가 같은 수준이며 겹치지 않는가?
- 사용자가 선택지 밖의 답을 제공할 수 있는가?
- 추천 이유가 현재 확정 설계에 근거하는가?
- 이미 알려진 내용을 다시 묻지 않는가?
- 후속 질문이 선행 답변과 논리적으로 연결되는가?
- 확정과 AI 추론이 시각적으로 구분되는가?
