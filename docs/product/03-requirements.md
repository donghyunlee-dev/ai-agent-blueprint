# 요구사항 명세

## 요구사항 표기

- `PJT`: 프로젝트와 저장
- `AUTH`: 사내 인증과 세션
- `AI`: AI 오케스트레이션, 프롬프트와 모델
- `CONV`: 대화와 질문
- `FORM`: 선택 폼
- `PROP`: 제안과 승인
- `DES`: 구조화 설계
- `DOC`: 문서
- `SRC`: 참고 자료
- `EXP`: 내보내기
- `NFR`: 비기능 요구사항

우선순위는 `P0` 필수, `P1` 중요, `P2` 후속 개선으로 구분한다.

## AI 오케스트레이션, 프롬프트와 모델

### AI-001 작업별 모델 정책 — P0

시스템은 AI 작업을 논리 profile로 분리하고 작업 난도에 맞는 모델과 reasoning 수준을 사용해야 한다.

수용 기준:

- 맥락형 질문·설명은 LIGHT(Luna), 답변 추출·추천·Requirements는 DEFAULT(Mini), 최종 PRD draft만 FINAL(Terra)을 사용한다.
- 물리 모델명은 서버 registry와 환경 설정에서 관리하며 제품 코드에 분산하지 않는다.
- MVP는 Luna, Mini, Terra 외 모델로 자동 승격하지 않으며 FINAL 호출은 기본 1회, repair 포함 최대 2회다.
- model unavailable에서 승인되지 않은 다른 모델로 조용히 fallback하지 않는다.

### AI-002 버전 관리된 프롬프트와 schema — P0

모든 AI 요청은 task별 prompt와 strict JSON Schema version을 가져야 한다.

수용 기준:

- response, GenerationJob과 요청 원장에 task, promptVersion, schemaVersion과 model profile을 기록한다.
- inline 임시 prompt로 production 요청을 만들지 않는다.
- 알 수 없는 version, 추가 필드와 존재하지 않는 참조 ID가 있으면 전체 결과를 거절한다.
- prompt/model/schema 변경은 golden eval을 다시 통과해야 한다.

### AI-003 상황별 응답 block — P0

AI는 질문, 설명, 추천, 제안 요약, 충돌, 준비도와 다음 행동을 허용된 block으로 반환할 수 있어야 한다.

수용 기준:

- 한 사용자 사건의 단일 응답이 최대 6개 block과 여러 atomic proposal을 함께 반환할 수 있다.
- AI는 HTML, script, 임의 UI component 이름을 반환하지 않는다.
- 질문 block은 catalog의 ID, answer mode, required와 stable option value를 변경하지 않는다.
- 알 수 없는 block은 text로 추정 표시하지 않고 `AI_INVALID_OUTPUT`으로 처리한다.

### AI-004 자유 답변과 복수 제안 — P0

하나의 자유 답변에서 현재 질문의 직접 답과 추가 설계 사실을 분리해 복수 변경안으로 제안해야 한다.

수용 기준:

- proposal 하나는 대상 하나와 변경 의도 하나만 가진다.
- 사실, 사용자 선호, 가정과 AI 추천을 구분한다.
- 한 응답의 최대 proposal 수를 제한하고 초과 내용은 후속 분석 대상으로 남긴다.
- 어떤 proposal도 사용자 승인 전 confirmed가 되지 않는다.

### AI-005 도움과 추천 분기 — P0

`잘 모르겠어요`와 `추천해 주세요`는 서로 다른 prompt와 결과 계약을 사용해야 한다.

수용 기준:

- 정적 도움말로 부족할 때만 LIGHT 설명을 사용하고 새 proposal 없이 같은 질문으로 돌아간다.
- 추천은 DEFAULT를 사용하며 근거, trade-off와 가정을 포함한 proposal을 반환한다.
- 근거가 부족하면 값을 추측하지 않고 필요한 정보를 표시한다.
- 추천값은 미리 선택하거나 자동 승인하지 않는다.

### AI-006 Token과 컨텍스트 예산 — P0

모든 AI 요청은 task별 입력·출력 token 한도와 프로젝트 전체 예산을 적용해야 한다.

수용 기준:

- 요청 전 token을 추정하고 상한의 85%에서 context 선별 또는 compaction을 수행한다.
- system/task/현재 대상/관련 confirmed 항목을 최근 대화보다 먼저 보존한다.
- provider의 자동 truncation으로 오래된 입력을 조용히 버리지 않는다.
- hard budget을 넘으면 provider 호출 없이 작업 대안과 이유를 표시한다.

### AI-007 다단계 문서 생성 — P0

Requirements와 PRD는 각각 결정론적 plan, draft, review와 선택적 repair 단계로 생성해야 한다.

수용 기준:

- `DocumentPlanBuilder`의 plan coverage 검증이 실패하면 draft API를 호출하지 않는다.
- draft는 section과 추적 가능한 구조화 항목으로 반환한다.
- review는 문서를 직접 수정하지 않고 issue와 coverage를 반환한다.
- 자동 repair는 문서당 최대 한 번, 문제 section만 변경한다.
- AI review를 통과해도 사용자의 ready 확인을 대신하지 않는다.

### AI-008 요청 원장과 관측성 — P0

프로젝트별 AI 호출 수, token, 지연, model과 version을 비식별 원장으로 추적해야 한다.

수용 기준:

- 입력, cached input, 출력과 reasoning token을 가능한 범위에서 구분한다.
- 사용자 원문, 파일 본문, token, 이메일과 secret을 원장에 기록하지 않는다.
- 같은 logical request의 중복 결과를 한 번만 반영한다.
- 일반 프로젝트의 예상 호출 수와 실제 차이를 QA에서 확인할 수 있다.

### AI-009 평가와 출시 gate — P0

모델, prompt 또는 schema 변경은 task별 자동 평가와 문서 정합성 gate를 통과해야 한다.

수용 기준:

- schema, ID, revision, coverage와 금지 결과를 deterministic assertion으로 검증한다.
- 미승인 확정, 질문 계약 변경, 핵심 문서 coverage 누락과 prompt injection 성공은 0건이어야 한다.
- 정성 grader만으로 출시를 승인하지 않는다.
- 후보가 품질이 같으면 token과 지연이 낮은 구성을 우선한다.

### AI-010 저장·보안·실패 정책 — P0

AI 요청은 사내 데이터를 불필요하게 보존하지 않고 실패 시 기존 상태를 지켜야 한다.

수용 기준:

- Responses API 요청에 `store: false`와 명시적 context 정책을 적용한다.
- schema 자동 재시도는 task당 1회이고 무한 재시도하지 않는다.
- rate limit과 timeout에서 모델을 승격하지 않는다.
- 실패한 응답 일부를 프로젝트나 문서에 반영하지 않는다.

## 사내 인증과 세션

### AUTH-001 AX Login 시작 — P0

비인증 사용자는 제품 홈보다 먼저 로그인 화면을 보고 AX Login의 사내 Microsoft 인증을 시작할 수 있어야 한다.

수용 기준:

- 로그인 화면에는 이메일·비밀번호 입력 없이 `Microsoft 계정으로 계속` 행동 하나를 제공한다.
- 보호 경로 접근 시 인증 확인이 끝나기 전에 제품 내용을 렌더링하지 않는다.
- 로그인 시작 전 same-origin 내부 경로만 `returnTo`로 보존한다.
- 인증된 사용자가 로그인 화면에 접근하면 홈 또는 검증된 `returnTo`로 이동한다.

### AUTH-002 AX token 검증과 세션 — P0

서버는 AX Auth의 일회용 token을 서버 간 요청으로 검증한 뒤 위조 방지된 Blueprint 세션을 발급해야 한다.

수용 기준:

- AX 검증 응답의 HTTP status가 아니라 `result.valid`로 성공을 판정한다.
- client ID가 설정과 일치할 때만 세션을 발급한다.
- 세션 cookie는 HttpOnly, SameSite=Lax, Path=/이며 운영에서는 Secure다.
- client secret, session secret과 login token은 브라우저 저장소·번들·로그에 남지 않는다.
- 만료, 재사용, client 불일치와 잘못된 token은 세션을 만들지 않는다.

### AUTH-003 보호 라우트와 API — P0

인증된 사내 직원만 제품 화면과 모든 Blueprint API를 사용할 수 있어야 한다.

수용 기준:

- `/`와 `/blueprints/*`는 유효한 세션이 없으면 로그인 흐름으로 전환한다.
- 모든 `/api/blueprint/*`는 공통 서버 세션 검증을 수행한다.
- 비인증 API 요청은 `401 AUTH_REQUIRED`를 반환하며 OpenAI 요청을 만들지 않는다.
- unsafe API method는 same-origin 요청만 허용한다.

### AUTH-004 사용자 세션과 로그아웃 — P0

사용자는 현재 로그인 계정을 확인하고 Blueprint 세션을 종료할 수 있어야 한다.

수용 기준:

- AppBar 또는 사용자 메뉴에 현재 이메일과 로그아웃 행동을 표시한다.
- 로그아웃은 멱등적으로 세션 cookie를 제거하고 메모리의 사용자·프로젝트 상태를 비운다.
- 세션 만료 시 입력을 잘못된 사용자 영역에 저장하지 않고 재로그인을 안내한다.
- AX/Microsoft 전체 계정 로그아웃으로 오해할 수 있는 문구를 사용하지 않는다.

### AUTH-005 사용자별 로컬 데이터 격리 — P0

같은 브라우저를 사용하는 서로 다른 직원의 로컬 Blueprint 프로젝트를 분리해야 한다.

수용 기준:

- IndexedDB 조회·저장·삭제에 현재 인증 사용자의 `ownerKey`를 적용한다.
- 사용자 전환 시 이전 사용자의 최근 프로젝트와 열린 aggregate를 표시하거나 Agent 요청에 포함하지 않는다.
- ownerKey에는 원문 이메일 대신 client ID와 정규화 이메일에서 파생한 안정적인 일방향 키를 사용한다.

## 프로젝트와 저장

### PJT-001 새 Blueprint 생성 — P0

사용자는 제목과 첫 설명으로 Blueprint 프로젝트를 생성할 수 있어야 한다.

수용 기준:

- 제목을 입력하지 않으면 첫 설명에서 안전한 임시 제목을 만든다.
- 생성 즉시 고유 프로젝트 ID와 생성 시간을 부여한다.
- 첫 설명은 대화 메시지와 Agent 분석 입력에 한 번만 기록한다.

### PJT-002 자동 저장과 복구 — P0

프로젝트의 대화, 설계, 제안, 문서와 참고 자료 메타데이터를 브라우저에 자동 저장해야 한다.

수용 기준:

- 확정, 편집, 메시지 추가 후 500ms 이내 저장을 예약한다.
- 새로고침 후 마지막 완료된 저장 상태를 복구한다.
- 저장 실패 시 작업은 유지하고 재시도 가능한 오류를 표시한다.

### PJT-003 프로젝트 재개 — P1

사용자는 최근 Blueprint 목록에서 작업을 다시 열 수 있어야 한다.

수용 기준:

- 제목, 최종 수정 시간, 준비도와 현재 작업 문서를 표시한다.
- 프로젝트를 열면 마지막 선택 탭과 대화 위치를 복원한다.

### PJT-004 프로젝트 보관 한도 — P0

브라우저에는 최근 사용 프로젝트를 최대 20개까지 보관해야 한다.

수용 기준:

- 21번째 프로젝트 저장 전 현재 프로젝트를 제외하고 `lastOpenedAt`이 가장 오래된 프로젝트를 정리 대상으로 표시한다.
- 사용자가 삭제를 확인해야 새 프로젝트 생성을 계속한다.
- 사용자가 취소하면 기존 프로젝트를 유지하고 새 프로젝트를 생성하지 않는다.
- 정리 대상 프로젝트의 대화, 설계, 문서와 첨부 자료 데이터를 함께 제거한다.
- 영구 삭제와 로컬 데이터의 복구 한계를 확인 화면에 안내한다.

### PJT-005 리빌드 이전 데이터와 경로 — P0

- 리빌드 이전 로컬 저장 데이터는 새 스키마로 변환하지 않는다.
- 새 저장소 namespace를 사용해 이전 데이터와 분리한다.
- `/survey`와 `/prd`에는 이전 화면이나 리다이렉트를 제공하지 않고 404를 표시한다.

## 대화와 질문

### CONV-001 첫 입력 분석 — P0

Agent는 첫 입력에서 제품 목표, 문제, 사용자, 기능, 제약 후보를 복수로 추출해야 한다.

수용 기준:

- 각 후보는 유형, 내용, 근거와 신뢰도를 포함한다.
- 입력에서 확인되지 않은 내용은 확정 사실로 제안하지 않는다.
- 추출할 정보가 없으면 입력 보완 질문을 제공한다.

### CONV-002 다음 질문 선택 — P0

시스템은 확정 설계와 미정 항목을 기준으로 다음 질문을 결정해야 한다.

수용 기준:

- 이미 확정된 의미를 반복해서 묻지 않는다.
- 필수 공백, 의존 관계, 영향 범위를 기준으로 우선순위를 계산한다.
- 한 번에 하나의 주요 질문을 표시한다.
- 질문을 건너뛰면 미정 상태를 보존하고 다음 질문을 계산한다.
- 현재 질문과 관련된 미처리 제안이 있으면 다음 시스템 질문을 표시하지 않는다.
- 미처리 제안이 있어도 사용자의 자유 대화 입력은 허용한다.

### CONV-003 대화 이력 사용 — P0

Agent 요청은 최근 대화와 관련된 확정 설계만 포함해야 한다.

수용 기준:

- 길이 제한을 넘으면 오래된 대화를 구조화 요약으로 대체한다.
- 문서 전체 대신 현재 작업에 필요한 섹션만 전달한다.
- 대화 요약과 원문 메시지의 출처를 구분한다.
- 프로젝트마다 하나의 대화 스레드만 생성하고 별도 대화방 생성 기능을 제공하지 않는다.

### CONV-004 작업 상태 표시와 중단 — P1

분석, 제안 작성, 문서 갱신, 검토 상태를 사용자에게 표시해야 한다.

수용 기준:

- 실행 중인 작업 이름을 표시한다.
- 사용자가 요청을 중단할 수 있다.
- 중단된 요청은 확정 설계를 변경하지 않는다.

### CONV-005 오류 후 재시도 — P0

AI 요청이 실패해도 사용자의 입력과 프로젝트 상태를 유지해야 한다.

수용 기준:

- 실패한 메시지를 다시 보낼 수 있다.
- 중복 재시도로 같은 제안이 여러 번 추가되지 않는다.
- 오류 원인과 다음 행동을 짧게 안내한다.
- AI 실패를 성공처럼 보이게 하는 fallback 제안이나 문서를 생성하지 않는다.

## 선택 폼

### FORM-001 허용 입력 유형 — P0

질문은 단일 선택, 복수 선택, 텍스트, 숫자, 범위, 순위, 확인 유형 중 하나로 렌더링해야 한다.

수용 기준:

- 서버 응답의 임의 컴포넌트나 HTML을 렌더링하지 않는다.
- 지원하지 않는 유형은 텍스트 입력으로 안전하게 대체한다.
- 모든 입력 유형을 키보드만으로 완료할 수 있다.

### FORM-002 선택지 계약 — P0

선택지는 안정적인 값과 사용자 문구를 분리해야 한다.

수용 기준:

- 각 선택지는 `value`, `label`, 선택적 설명을 가진다.
- 추천 선택지는 추천 이유를 함께 표시하고 미리 선택하지 않는다.
- 복수 선택에서는 선택 순서와 우선순위를 동일하게 취급하지 않는다.

### FORM-003 직접 입력과 불확실성 — P0

질문 정책에 따라 직접 입력, 추천 요청과 나중에 결정을 제공해야 한다.

수용 기준:

- 직접 입력은 선택 항목과 함께 제출할 수 있다.
- 추천 요청은 추천안과 근거를 제안 상태로 반환한다.
- 나중에 결정은 명시적 미정 항목을 생성한다.

### FORM-004 조건부 질문 — P0

후속 질문은 관련 선행 결정이 존재할 때만 활성화해야 한다.

수용 기준:

- 로그인이 불필요하면 로그인 방식 질문을 생략한다.
- 데이터 저장이 불필요하면 데이터베이스 종류를 묻지 않는다.
- 선행 결정이 변경되면 종속 항목을 자동 삭제하지 않고 재검토 상태로 전환한다.
- 선행 결정에 따라 질문 대상이 명백히 필요 없으면 사용자 확인 결과를 `not_applicable`로 저장하고 미정 상태와 구분한다.

## 제안과 승인

### PROP-001 복수 제안 생성 — P0

하나의 답변 또는 자료에서 여러 설계 변경안을 생성할 수 있어야 한다.

수용 기준:

- 각 제안은 하나의 대상과 하나의 변경 의도를 가진다.
- 추가, 수정, 삭제를 구분한다.
- 제안별 이유와 근거를 표시한다.

### PROP-002 개별 처리 — P0

사용자는 각 제안을 승인, 수정 또는 거절할 수 있어야 한다.

수용 기준:

- 일부 제안만 승인할 수 있다.
- 수정 후 승인하면 수정된 값만 확정된다.
- 거절한 제안은 확정 설계와 문서에 반영되지 않는다.

### PROP-003 충돌 검토 — P0

새 제안이 기존 확정 항목과 충돌하면 두 값을 비교해야 한다.

수용 기준:

- 기존 값, 새 값, 각각의 근거를 표시한다.
- 사용자가 선택할 때까지 기존 확정 값을 유지한다.
- 충돌 해결 결과를 변경 이력에 남긴다.

### PROP-004 일괄 처리 — P1

여러 제안을 한 번에 승인하거나 거절할 수 있어야 한다.

수용 기준:

- 충돌 또는 검증 오류가 있는 제안은 일괄 승인에서 제외한다.
- 실행 전 처리 대상 수를 표시한다.

## 구조화 설계

### DES-001 설계 항목 관리 — P0

제품 목표, 문제, 사용자, 범위, 기능, 제약, 기술 결정, 성공 기준과 위험을 항목 단위로 관리해야 한다.

수용 기준:

- 모든 항목은 고유 ID, 유형, 상태, 내용과 근거를 가진다.
- 확정 항목은 관련 문서 섹션에서 추적할 수 있다.
- 항목 삭제는 변경 제안 승인을 통해 처리한다.

### DES-002 요구사항과 수용 기준 — P0

핵심 기능은 요구사항과 검증 가능한 수용 기준으로 구체화해야 한다.

수용 기준:

- 요구사항은 설명, 우선순위와 상태를 가진다.
- 수용 기준은 관찰 가능한 결과로 작성한다.
- 수용 기준이 없는 핵심 요구사항을 검토 항목으로 표시한다.

### DES-003 준비도 계산 — P0

시스템은 필수 설계 영역의 상태로 문서 준비도를 계산해야 한다.

수용 기준:

- 답변 개수나 숫자 점수만으로 완료 처리하지 않는다.
- 확정, 미정과 누락을 구분한다.
- 해당 없음은 `not_applicable`로 표시하며 deferred 또는 missing으로 계산하지 않는다.
- 준비도 상세에서 부족한 영역으로 이동할 수 있다.
- 화면에는 `insufficient`, `workable`, `ready` 상태와 영역별 상태를 표시하고 숫자 점수를 표시하지 않는다.
- 핵심 정보 누락이나 처리되지 않은 충돌은 문서 생성을 막고, 명시적 미정은 생성을 막지 않는다.

## 문서

### DOC-001 공통 설계 기반 생성 — P0

요구사항명세서와 PRD는 같은 확정 설계 스냅샷에서 생성해야 한다.

수용 기준:

- 생성 결과에 사용한 설계 버전을 기록한다.
- 미정과 가정을 별도 섹션에 표시한다.
- 제안 상태의 항목을 확정 사실로 작성하지 않는다.

### DOC-002 요구사항명세서 — P0

요구사항명세서는 기능·비기능 요구사항, 데이터, 연동, 권한, 예외, 배포와 수용 기준을 포함해야 한다.

수용 기준:

- 각 요구사항에 추적 가능한 ID를 표시한다.
- 핵심 기능과 수용 기준을 연결한다.
- 제외 범위와 오픈 이슈를 포함한다.

### DOC-003 PRD — P0

PRD는 개요, 문제, 목표, 사용자, 시나리오, 범위, 성공 기준, 위험과 출시 계획을 포함해야 한다.

수용 기준:

- 요구사항명세서와 동일한 제품 목표와 사용자를 사용한다.
- 기능의 기술 구현 세부사항보다 제품 결과를 우선한다.
- 범위와 제외 범위를 구분한다.
- 같은 프로젝트의 요구사항명세서가 `ready` 상태일 때만 생성을 허용한다.
- 요구사항명세서가 준비되지 않았으면 부족한 검토 항목으로 이동하는 행동을 제공한다.

### DOC-004 직접 편집 — P1

사용자는 문서 섹션을 직접 수정할 수 있어야 한다.

수용 기준:

- 편집 내용은 자동 저장한다.
- 생성 원문과 사용자 편집 여부를 기록한다.
- 저장 전에 연결된 공통 설계 항목과 영향받는 다른 문서를 미리 표시하고 확인받는다.
- 확인 후 연결된 공통 설계 항목을 사용자 확정 변경으로 같은 저장 작업에서 갱신한다.
- 변경 근거를 `user_edit`로 기록하고 설계 revision을 증가시킨다.
- 같은 설계 항목을 참조하는 다른 문서 섹션을 `stale`로 표시한다.

### DOC-005 부분 AI 보완 — P1

사용자는 선택한 섹션 또는 요구사항만 Agent에 보완 요청할 수 있어야 한다.

수용 기준:

- 변경 대상 범위를 요청 전에 표시한다.
- 전체 문서를 불필요하게 재생성하지 않는다.
- 변경은 제안 상태로 표시하고 승인 후 반영한다.

### DOC-006 정합성 검토 — P1

시스템은 문서 간 목표, 사용자, 범위와 요구사항의 충돌을 검토해야 한다.

수용 기준:

- 불일치 위치와 관련 설계 항목을 표시한다.
- 자동 수정은 변경 제안으로 제공한다.

### DOC-007 설정 가이드 생성 — P0

Agent는 확정 설계와 참고 자료를 사용해 프로젝트별 설정 가이드 전체를 새로 작성해야 한다.

수용 기준:

- 설치, 환경 설정, 연동 순서, 검증과 주의사항을 포함한다.
- 사용자 승인 전까지 생성 결과를 `draft`로 표시한다.
- 확인되지 않은 버전이나 명령을 확정 사실처럼 표시하지 않는다.
- 요구사항명세서와 PRD의 확정 기술 결정을 변경하지 않는다.

## 참고 자료와 내보내기

### SRC-001 파일 첨부 — P0

사용자는 프로젝트 시작 또는 대화 중 참고 파일을 첨부할 수 있어야 한다.

수용 기준:

- 파일명, 유형, 크기, 추출 상태를 표시한다.
- TXT, Markdown과 텍스트 추출 가능한 PDF만 허용한다.
- 파일당 최대 10MB, 프로젝트당 최대 5개로 제한한다.
- PDF는 문단 단위 텍스트를 추출하고 표 구조는 일반 텍스트로 평탄화한다.
- 읽기 실패 파일과 이유를 표시한다.
- 추출이 완료되지 않은 파일을 Agent 입력에 포함하지 않는다.

### SRC-002 근거 연결 — P1

자료에서 추출한 설계 항목은 원본 파일과 인용 위치를 근거로 연결해야 한다.

수용 기준:

- 사용자가 근거 미리보기를 열 수 있다.
- 원본이 제거되면 관련 항목에 근거 없음 상태를 표시한다.

### EXP-001 Markdown 내보내기 — P0

사용자는 요구사항명세서, PRD와 설정 가이드를 복사하거나 Markdown으로 다운로드할 수 있어야 한다.

수용 기준:

- 요구사항명세서, PRD와 설정 가이드를 문서별로 복사하거나 다운로드할 수 있다.
- 전체 묶음 또는 ZIP 내보내기는 MVP에 포함하지 않는다.
- 파일명은 프로젝트명과 문서 유형을 포함한다.
- 화면용 제어 요소가 Markdown 내용에 포함되지 않는다.

## 비기능 요구사항

### NFR-001 접근성 — P0

- 핵심 흐름은 키보드로 완료할 수 있어야 한다.
- 폼은 이름, 설명, 오류와 선택 상태를 보조 기술에 전달해야 한다.
- 텍스트와 상태 표현은 WCAG AA 대비를 충족해야 한다.
- 색상만으로 제안 상태를 구분하지 않아야 한다.

### NFR-002 반응형 — P0

- 1280px 이상에서는 대화, 작업 영역, 상세 패널을 함께 사용할 수 있어야 한다.
- 태블릿에서는 상세 패널을 오버레이로 전환할 수 있어야 한다.
- 모바일에서는 대화, 설계, 검토를 탭으로 전환하고 입력창을 항상 접근 가능하게 유지해야 한다.

### NFR-003 성능 — P1

- 초기 앱 셸은 일반적인 광대역 환경에서 2.5초 이내 상호작용 가능 상태를 목표로 한다.
- 긴 대화와 문서는 가상화 또는 구간 렌더링을 적용할 수 있어야 한다.
- 자동 저장과 Agent 요청이 입력 반응을 차단하지 않아야 한다.

### NFR-004 보안과 개인정보 — P0

- OpenAI API 키는 서버 환경에만 둔다.
- AX client secret과 Blueprint session secret은 서버 환경에만 둔다.
- 인증 token과 session cookie 값을 로그, URL 잔존 상태와 클라이언트 저장소에 기록하지 않는다.
- 업로드 텍스트와 프로젝트 데이터는 요청 목적에 필요한 범위만 전송한다.
- 오류 로그에 프로젝트 원문, 파일 내용, 토큰을 기록하지 않는다.
- 외부 콘텐츠를 명령이 아닌 참고 자료로 취급한다.
- 프로젝트별 첫 AI 전송 전에 외부 AI 처리와 전송 범위를 한 번 안내한다.
- 파일별로 민감정보 제거를 권고하고 현재 작업에 필요한 발췌만 전송한다.

### NFR-005 관측성과 오류 — P1

- Agent 요청에 상관관계 ID와 작업 유형을 기록한다.
- 개인 데이터를 제외한 상태 코드, 지연 시간과 스키마 실패를 측정한다.
- 사용자에게 내부 스택이나 공급자 원문 오류를 노출하지 않는다.

### NFR-006 언어 — P0

- MVP의 사용자 인터페이스는 한국어로 제공한다.
- Agent 질문, 제안, 오류와 생성 문서는 한국어로 작성한다.
- 다국어 전환과 영문 문서 생성은 MVP 범위에 포함하지 않는다.

### NFR-007 제품 분석 — P0

- MVP는 운영 사용자 행동 이벤트를 수집하지 않는다.
- 성공 지표는 사용자 테스트와 QA 결과로 검증한다.
- 오류 진단을 위한 비식별 상태 코드와 지연 시간은 제품 행동 분석과 분리한다.
