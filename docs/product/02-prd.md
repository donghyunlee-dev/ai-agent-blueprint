# Agent Blueprint PRD

## 문서 목적

이 문서는 Agent형 Blueprint의 제품 목표, 사용자 경험, 범위와 단계별 개발 결과를 정의한다. 상세 동작은 요구사항 명세와 대화 프로세스, 구현 계약은 데이터 명세와 아키텍처를 따른다.

## 제품 비전

사용자는 복잡한 기획 양식을 먼저 학습하지 않고도 아이디어와 기존 자료로 설계를 시작한다. Blueprint Agent는 현재까지 확정된 맥락을 읽고 필요한 질문을 이어가며, 답변을 제품 결정과 요구사항으로 구조화한다. 사용자는 AI 제안을 검토하고 확정하며 요구사항명세서와 PRD를 같은 작업 공간에서 완성한다.

## 목표

- Google 계정으로 로그인한 사용자만 제품 화면과 Blueprint API를 사용하게 한다.
- 간단한 질문, 설계 분석과 최종 문서 작성에 서로 다른 모델·reasoning·token 정책을 적용한다.
- 한 AI 응답에서 상황에 맞는 질문·설명·추천·복수 제안 block을 안전하게 제공한다.
- 프로젝트별 AI 호출·token 예산을 관리하면서 Requirements와 PRD 품질을 자동 평가한다.
- 첫 입력 후 1분 안에 첫 번째 검토 가능한 설계 제안을 제공한다.
- 사용자가 이미 제공한 정보를 반복 질문하지 않는다.
- 한 답변에서 발견된 여러 설계 항목을 개별 검토할 수 있게 한다.
- 요구사항명세서와 PRD가 하나의 확정 설계를 참조하게 한다.
- 생성된 문서의 특정 항목을 대화 또는 직접 편집으로 수정할 수 있게 한다.
- 오류, 새로고침과 재시도 이후에도 프로젝트 작업을 이어갈 수 있게 한다.

## 비목표

- 범용 문서 편집기 제공
- 화면 설계와 와이어프레임 자동 생성
- 복수 사용자의 실시간 동시 편집
- 외부 업무 시스템에 이슈 생성
- 기술 결정을 사용자 승인 없이 자동 적용
- 생성 결과가 법률·보안·개발 검토를 대체한다고 보장

## 핵심 사용자 여정

### 여정 0: 사용자 로그인

1. 사용자가 보호된 제품 경로에 접근한다.
2. 시스템이 Blueprint 세션을 확인하고 비인증 상태면 로그인 화면을 표시한다.
3. 사용자가 `Google로 시작하기`를 선택한다.
4. Google 인증을 완료하고 서버 callback에서 state, nonce, ID token과 검증된 email claim을 확인한다.
5. 서버가 검증된 OIDC identity로 Blueprint HttpOnly session을 발급한다.
6. 사용자는 홈 또는 원래 접근한 보호 경로로 이동한다.

### 여정 A: 아이디어에서 시작

1. 사용자가 Blueprint 이름과 만들고 싶은 제품을 설명한다.
2. Agent가 목표, 문제, 사용자, 기능 후보를 추출한다.
3. 사용자가 추출된 항목을 승인하거나 수정한다.
4. 사용자는 대화를 계속하고 Agent는 빠진 결정이 중요할 때만 맥락에 맞는 후속 질문이나 선택 카드를 제시한다.
5. 대화에서 추출한 제안은 사용자가 승인해야 확정된다. 오른쪽 요약은 현재 확정 내용과 남은 결정을 각각 보여주고 출처 대화로 연결한다.
6. 확인된 설계는 그룹 카드나 출처를 따라갈 수 있는 읽기 전용 도식으로 살펴볼 수 있다. 도식에 필요한 근거가 없으면 텍스트 요약을 제공한다.
7. 문서 준비도가 충족되면 사용자가 별도 `요구사항 명세` 단계에서 생성을 요청하고 검토한다.
8. 요구사항 명세가 준비 완료되면 사용자가 PRD 생성을 요청한다.
9. 사용자가 남은 결정을 검토하고 문서를 내보낸다.

### 여정 B: 기존 자료에서 시작

1. 사용자가 회의록, Markdown 또는 텍스트 자료를 첨부한다.
2. 시스템이 텍스트 추출 결과와 실패 여부를 표시한다.
3. Agent가 자료에서 확인 가능한 사실, 가정과 제안 후보를 분리한다.
4. 사용자가 필요한 후보를 승인·수정·거절한다.
5. Agent가 자료와 대화에서 해소되지 않은 핵심 결정만 맥락에 맞게 묻는다.
6. 확정된 근거를 바탕으로 사용자가 별도 단계에서 문서를 생성한다.

### 여정 C: 생성된 문서 보완

1. 사용자가 PRD 또는 요구사항명세서의 항목을 선택한다.
2. 직접 수정하거나 Agent에 개선을 요청한다.
3. Agent가 변경 내용과 영향받는 항목을 제안한다.
4. 사용자가 변경안을 개별 또는 일괄 처리한다.
5. 승인된 변경이 공통 설계와 관련 문서에 반영된다.

## 핵심 기능

### Google 인증

- Google OAuth/OIDC 기반 로그인과 verified email 확인
- 서버 검증 Blueprint 세션과 보호 라우트
- 모든 Blueprint API의 서버 측 인증
- 현재 사용자 표시, 로그아웃과 세션 만료 재인증
- 사용자별 로컬 프로젝트 분리

### 프로젝트 작업 공간

- 새 Blueprint 생성
- 로컬 프로젝트 자동 저장과 재개
- 대화, 설계, 요구사항명세서, PRD, 참고 자료 탭 제공
- 프로젝트 상태와 문서 준비도 표시

### Agent 대화

- 카탈로그 질문을 완료하지 않아도 진행할 수 있는 연속 자유 대화
- 필요한 때만 대화 안에 맥락형 질문·선택 카드 제공
- 답변과 첨부 자료에서 여러 설계 항목 추출
- 사용자가 명시적으로 추천을 요청하면 근거가 충분한 11개 대안을 제공하고 선택한 안만 제안 검토로 연결
- 좌측 대화와 우측 확정 내용·남은 결정 요약을 같은 저장 상태로 연결
- 확정 데이터에서 파생한 그룹 요약과 선택적 도식 보기, 텍스트 대체 제공
- 분석, 문서 작성, 검토 등 작업 진행 상태 표시
- `잘 모르겠어요`, 추천 요청, 자유 답변과 문서 작성에 분리된 AI task 사용
- 하나의 turn에서 여러 UI block과 atomic proposal 반환

### AI 품질과 비용 제어

- LIGHT(Luna)·DEFAULT(Mini)·FINAL(Terra) 논리 모델 profile
- task별 reasoning, 입력·출력 token과 timeout 한도
- versioned prompt/schema와 ContextManifest
- 프로젝트별 호출·token 원장과 soft/hard budget
- Requirements/PRD plan-draft-review-repair pipeline
- 모델·prompt 변경 전 golden eval과 release gate

### 선택 폼

- 단일 선택, 복수 선택, 직접 입력, 숫자·범위, 순위, 확인 폼 지원
- 표준 값과 화면 문구 분리
- `잘 모르겠어요`, `추천해 주세요`, `나중에 결정` 상태 지원
- 조건에 맞는 후속 질문 활성화

### 제안 검토

- 추가, 수정, 삭제 제안을 구분
- 제안별 대상, 값, 이유와 근거 표시
- 개별 승인·수정·거절
- 충돌 발생 시 기존 값과 새 값을 비교
- 승인된 내용만 확정 설계에 반영

### 설계와 문서

- 제품 목표, 사용자, 범위, 기능, 제약, 기술 결정을 구조화
- 요구사항별 설명, 우선순위, 상태와 수용 기준 관리
- 공통 설계에서 요구사항명세서와 PRD 생성
- 문서 섹션 직접 편집과 부분 AI 보완
- 문서 간 불일치와 미정 항목 검토

### 참고 자료와 내보내기

- 텍스트 기반 파일 업로드와 추출 상태 표시
- 추출 내용의 미리보기와 설계 항목 근거 연결
- 확정 설계에 맞춘 설정 가이드 전체 생성
- 요구사항명세서, PRD, 설정 가이드 Markdown 복사·다운로드

## 문서 준비도

준비도는 답변 개수나 숫자 점수가 아니라 필수 결정의 상태로 판단한다.

| 영역 | 준비 조건 |
| --- | --- |
| 제품 정의 | 해결 문제, 목표, 핵심 사용자가 확정됨 |
| 범위 | 핵심 기능과 제외 범위가 확정됨 |
| 요구사항 | 핵심 기능에 설명과 수용 기준이 존재함 |
| 운영 | 데이터, 권한, 배포와 주요 제약이 결정 또는 미정으로 명시됨 |
| 검증 | 성공 기준과 주요 위험이 작성됨 |

핵심 정보가 누락되지 않고 처리되지 않은 충돌이 없으면 문서를 생성할 수 있다. 명시적 미정은 생성을 막지 않으며 문서의 오픈 이슈로 표시한다. 화면에는 `부족`, `작업 가능`, `준비 완료`와 영역별 상태만 표시한다.

## 확정된 운영 정책

- 홈보다 Google 로그인을 먼저 제공하며 비인증 사용자는 제품과 Blueprint API에 접근할 수 없다.
- Google authorization code와 OIDC ID token은 서버에서 검증하고 Blueprint HttpOnly session으로 교환한다. scope는 `openid email`이며 Gmail API를 요청하지 않는다.
- 대화 응답과 맥락형 후속 질문·선택 데이터는 `TURN_ANALYZE` DEFAULT, 명시적 추천은 `OPTION_RECOMMEND` DEFAULT를 사용한다. 요구사항 명세서 draft/review는 DEFAULT, 최종 PRD draft만 FINAL을 사용한다. 모든 동적 표시 데이터는 strict schema로 검증한다. 기존 `QUESTION_COMPOSE`/고정 문구 흐름은 현재 runtime 기록이며 CON-PR-05에서 목표 동작으로 대체한다.
- AI가 process state, readiness와 사용자 확정 여부를 결정하지 않는다.
- Requirements와 PRD는 plan, draft, review, 선택적 1회 repair로 생성한다.
- AI 응답은 허용된 DisplayBlock과 strict schema로만 렌더링한다.
- 일반 프로젝트는 약 17~21회 AI 호출과 프로젝트당 $0.60 hard 비용 상한을 기준으로 설계한다.
- Google 계정으로 로그인할 수 있으며 조직 도메인 allowlist를 두지 않는다.
- 로컬 프로젝트는 최근 사용 순으로 최대 20개를 보관한다. 초과 시 현재 프로젝트를 제외한 가장 오래된 프로젝트를 정리 대상으로 제시하고 사용자 확인 후 삭제한다.
- 문서 직접 편집은 연결된 공통 설계 항목에 사용자 확정 변경으로 자동 반영한다.
- 문서 저장 전에 영향받는 공통 설계 항목과 다른 문서를 미리 보여주고 사용자 확인을 받는다.
- 참고 자료는 TXT, Markdown과 텍스트 추출 가능한 PDF를 파일당 10MB, 프로젝트당 최대 5개까지 지원한다.
- PDF는 문단 중심으로 추출하고 표는 일반 텍스트로 변환한다.
- 현재 질문과 관련된 AI 제안을 모두 처리해야 다음 시스템 질문으로 이동한다. 자유 대화 입력은 계속 허용한다.
- AI 실패 시 fallback 결과를 생성하지 않고 입력과 확정 설계를 보존한 뒤 재시도를 제공한다.
- 전체 묶음 파일은 제공하지 않고 요구사항명세서, PRD와 설정 가이드를 각각 Markdown으로 복사하거나 다운로드한다.
- AI 데이터 사용 안내는 프로젝트별 최초 전송 전에 한 번 표시하고, 파일마다 민감정보 주의를 표시한다.
- MVP의 UI와 생성 문서는 한국어만 지원한다.
- 프로젝트마다 하나의 연속 대화만 제공한다.
- 요구사항명세서가 `ready` 상태가 된 뒤에만 PRD를 생성한다.
- 설정 가이드는 Agent가 확정 설계와 참고 자료를 바탕으로 전체 내용을 새로 작성한다.
- 프로젝트를 `completed`로 표시하려면 사용자가 설정 가이드를 승인해 `ready` 상태로 만들고, 문서 revision이 현재 설계 revision과 일치하며 모든 section이 current여야 한다. `draft`, `review_required`, stale/conflict 상태로는 완료할 수 없다(`DEC-045`).
- 추출 결과는 앱에서 읽기 전용이며 사용자는 결과를 내려받아 외부에서 수정할 수 있다(`DEC-044`).
- 리빌드 이전 로컬 데이터는 마이그레이션하지 않으며 `/survey`, `/prd`는 404로 처리한다.
- 운영 행동 분석을 수집하지 않고 사용자 테스트와 QA로 성공 지표를 검증한다.

## 성공 지표

### 사용성

- 새 프로젝트 사용자의 80% 이상이 도움 없이 첫 제안을 확정한다.
- 유효한 첫 입력부터 첫 제안 표시까지 중앙값 60초 이하를 목표로 한다.
- 문서 생성 전 동일 의미의 반복 질문 비율을 5% 이하로 유지한다.

### 결과 품질

- 핵심 기능의 90% 이상에 최소 한 개의 검증 가능한 수용 기준이 존재한다.
- PRD와 요구사항명세서의 목표·사용자·범위 불일치가 자동 검토에서 0건이어야 한다.
- 최종 문서에 확정되지 않은 내용을 확정 사실로 표시하는 오류가 없어야 한다.
- golden fixture에서 질문 계약 변경, 존재하지 않는 참조 ID와 미승인 자동 확정이 0건이어야 한다.
- Requirements 핵심 기능 coverage와 P0 수용 기준 coverage가 100%여야 한다.

### 신뢰성

- AI 요청 실패 후 입력과 확정 설계 보존율 100%
- 새로고침 후 마지막 자동 저장 상태 복구 성공률 99% 이상
- 잘못된 구조화 응답이 UI 상태를 변경하지 않도록 스키마 검증 실패를 안전하게 처리
- 일반 프로젝트의 AI 호출이 약 17~21회 범위에서 완료되고 hard token·비용 budget을 초과하지 않음
- model·prompt·schema 변경 전후 golden eval 통과율 100%

## 출시 단계

### 인증 선행 단계: Google 로그인

Google Cloud OAuth client와 환경별 callback 설정을 준비한 뒤 Google 로그인, 서버 session, API 보호, 사용자별 로컬 저장 격리를 먼저 완성한다. 이 단계를 통과하기 전에는 홈과 이후 기능을 출시하지 않는다.

개발 순서는 Google OAuth consent screen/client와 callback 설정 → `AUTH-PR-01` 서버 callback·OIDC 검증·session → `AUTH-PR-02` 로그인 화면·보호 route/API → `AUTH-PR-03` `(issuer, sub)` 기반 로컬 저장 격리 → `FND-PR-01`~`FND-PR-03` 구현 기반이다. 각 unit은 앞선 PR이 병합된 후 시작한다.

### 1단계: 프로젝트 기반

프로젝트 모델, 로컬 저장소, 통합 작업 공간과 공통 라우팅을 완성한다. 새로고침 후 대화와 설계 상태를 복구할 수 있어야 한다.

### 2단계: 대화와 설계 결정

연속 자유 대화, 필요할 때만 보이는 context-derived 선택 카드, 근거가 연결된 제안 검토와 우측 결정 요약을 한 사용자 여정으로 완성한다. 현행 fixed `QUESTION_CATALOG`는 교체 대상이며, UI renderer type만 strict allowlist로 유지한다. 명시적 추천 요청은 맥락이 충분할 때만 dynamic grounded 후보 11개를 제공하고, 선택은 pending proposal을 만든 뒤 사용자 승인으로 확정한다.

AI task router, LIGHT/DEFAULT profile, 상황별 DisplayBlock, prompt/schema version, 11개 추천의 token-budget 평가와 대화 호출 예산을 함께 완성한다. AI는 사실을 제안할 수 있지만 확정·readiness·문서 상태는 정하지 않는다.

### 3단계: 구조화 설계

제품 정의, 기능, 제약, 기술 결정과 수용 기준을 항목 단위로 관리한다. 항목 수정과 충돌 해결이 다른 확정 데이터를 제거하지 않아야 한다.

### 4단계: 문서 작업 공간

공통 설계에서 요구사항명세서와 PRD를 생성하고 같은 화면에서 읽기·직접 편집·부분 보완할 수 있어야 한다.

결정론적 plan, Mini Requirements, Terra 최종 PRD draft와 Mini review를 사용하는 pipeline과 문서 품질 gate를 함께 완성한다.

### 5단계: 자료와 내보내기

참고 파일 추출, 근거 연결, 실행 가이드 추천과 문서별 내보내기를 완성한다.

### 6단계: 품질과 출시 준비

문서 정합성 검토, 오류 복구, 접근성, 데스크톱·모바일 사용성과 전체 E2E 흐름을 검증한다.

## 출시 조건

- task별 model/reasoning/token 설정과 prompt/schema version이 요청 원장에서 추적된다.
- AI golden eval에서 미승인 확정, 질문 계약 변경, 존재하지 않는 참조와 문서 핵심 coverage 누락이 0건이다.
- 일반 프로젝트의 호출 수가 기준 예산 안에서 Requirements와 PRD까지 완료된다.
- 비인증 접근, 만료·위조 세션과 직접 API 호출이 차단된다.
- Google 로그인 성공 후 원래 보호 경로로 복귀하고 로그아웃 후 로컬 작업 상태가 화면에서 제거된다.
- 필수 요구사항의 수용 기준이 자동 테스트 또는 브라우저 검증으로 확인된다.
- 대화 시작부터 요구사항명세서와 PRD 다운로드까지 중단 없는 정상 흐름이 동작한다.
- OpenAI 실패, 잘못된 응답, 파일 추출 실패와 저장 실패 상태가 사용자 입력을 잃지 않는다.
- 데스크톱과 모바일에서 대화, 설계 검토, 문서 편집과 내보내기가 가능하다.
- API 키, Google OAuth secret, 로그인 token과 참고 자료 내용이 브라우저 로그나 저장소에 노출되지 않는다.
