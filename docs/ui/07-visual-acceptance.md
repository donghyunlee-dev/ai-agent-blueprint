# 시각 QA와 완료 판정

## 목적

개발자가 “구현했다”고 판단하는 기준과 검토자가 “설계대로 보인다”고 판단하는 기준을 동일하게 만든다. 시각 검수는 스크린샷 비교만이 아니라 위치, 상태, 행동과 접근성을 함께 확인한다.

## 화면별 검증 범위

상태 fixture와 전이 기준은 [화면 상태 매트릭스](screen-state-matrix.md), annotation별 기대 결과는 [상태별 화면 청사진](screens/README.md)을 따른다.

아래 표는 전체 화면 개편의 상태·viewport 목록이다. 개별 UIR UI PR은 변경 화면의 1440×900·390×844와 영향을 받은 상태를 최종 HEAD에서 캡처한다. 중간 viewport는 해당 PR이 직접 영향을 주는 배치와 전환을 검증한다. QLT-PR-01에서 전체 5개 기준 viewport와 화면 상태를 통합 감사한다. 문서 전용 UIR-PR-01에는 화면 캡처를 요구하지 않는다.

## 시안과 구현 화면의 직접 비교

제품 동작·보안·접근성·반응형 계약을 먼저 지킨다. 화면 배치의 주 기준은 [`docs/blueprint-design/README.md`](../blueprint-design/README.md)가 연결한 해당 시안이다. 새 시안에 없는 상태에만 [`docs/template/README.md`](../template/README.md)를 보조 기준으로 사용한다. 시안의 가상 데이터·미지원 기능·사진·로고를 구현에 추가하지 않는다.

UI PR마다 변경 화면의 기준 이미지와 실제 렌더를 **같은 CSS viewport와 비교 가능한 상태**로 나란히 놓고 직접 확인한다. 디자인 보드 일부를 쓰면 해당 패널만 자른다. 기준 이미지의 크기나 종횡비가 다르면 비율을 유지해 같은 viewport 좌표계로 정렬하고, 여백·잘림·배율을 기록한다. 픽셀 비교를 위해 이미지를 가로세로로 늘이지 않는다. 시안에 없는 오류·빈 상태는 보조 이미지와 비교하거나 비교 불가능한 영역 및 이유를 명시한다.

각 비교 기록에는 주 시안 파일 경로, 보조 이미지 경로가 있다면 그 경로, 실제 route·상태, CSS viewport, 구현 HEAD SHA, 렌더 캡처 artifact 링크를 넣는다. 가능한 주요 anchor인 왼쪽 rail, 상단 header, 주 콘텐츠 경계, hero, composer, 최근 프로젝트 영역의 `x/y/너비/높이`를 기준 이미지와 렌더 이미지에서 측정한다. `x/y` 차이는 px와 viewport 너비·높이에 대한 %, 너비·높이 차이는 px와 기준 anchor 크기에 대한 %를 함께 적는다. 해당 화면에 없는 anchor는 `해당 없음`으로 기록한다.

주요 anchor의 위치 차이가 viewport 해당 축의 **5% 초과**이거나 너비·높이 차이가 기준 anchor의 **10% 초과**이면 실질적인 시각 차이로 판정한다. 제품·접근성·보안·반응형 계약을 지키기 위해 필요한 차이는 근거와 영향을 기록하면 예외로 인정한다. 설명되지 않은 실질 차이는 수정 대상이며 코드 리뷰와 QA를 `pass`로 처리하거나 PR을 `ready_to_merge`로 전환할 수 없다. 글꼴 래스터링과 안티앨리어싱 차이만으로는 실패 처리하지 않는다.

독립 코드 리뷰어와 QA는 각각 같은 화면 쌍을 직접 보고 실질 차이와 예외를 기록한다. Vercel UI Preview를 사용할 수 있으면 배포가 검토 중인 HEAD와 일치하는지 확인하고, 보호된 Preview는 기존 Vercel 인증 절차로 접근한다. Preview를 사용할 수 없으면 그 사실을 밝히고 로컬 렌더 증거로 시각 비교를 수행한다. 테스트 인증 mock은 화면 표현 검증 증거일 뿐 실제 계정·인증 동작의 증거가 아니다.

## 기하 검수

- 공통 프레임과 단계 탐색의 현재 위치가 모든 화면에서 일관된다.
- 데스크톱은 선택한 단계의 주 작업 영역이 가장 넓고 보조 영역이 주 행동을 밀어내지 않는다.
- 대화 composer, 지역 header와 상세 footer가 콘텐츠를 덮지 않는다.
- 인접한 동일 관계는 같은 spacing token을 사용한다.
- 문서 본문은 읽기 좋은 폭으로 제한하고 목차·섹션 이동과 함께 동작한다.
- 390px에서 수평 스크롤이 없고 고정 행동이 마지막 콘텐츠를 가리지 않는다.

## 화면 구현 검수

- UI는 관련 `docs/blueprint-design/` 주 시안과 필요할 때 `docs/template/` 상태 fallback의 정보 위계·배치·상태를 반영한다.
- 버튼, 링크, 입력, 선택, 탭, 대화상자는 `component-contracts.md`의 semantic contract를 따른다.
- 상태는 읽을 수 있는 텍스트와 필요한 경우 아이콘/색상을 함께 사용한다.
- 재사용 로컬 컴포넌트는 실제 공유 동작이 있는 범위에 한정한다.
- 시안에만 있는 메뉴, 샘플 데이터, 자산과 기능을 화면에 넣지 않았다.

## 토큰 검수

다음 검색 결과가 0이어야 한다. 단, `--bp-*` 구조 변수 선언과 테스트 fixture는 예외다.

- 제품 CSS의 hex/rgb/hsl 색상
- 프로젝트 공통 UI 기준이 없는 임의의 `--color-*` 재정의
- 컴포넌트마다 반복되는 raw padding/gap/radius/shadow
- 브랜드 색을 직접 참조하는 base palette

색상과 간격은 참고 캡처와 `docs/ui/00-visual-foundation.md`의 앱 소유 CSS 변수를 일관되게 사용한다.

## 상태와 행동 검수

각 부분 화면에서 다음 질문에 모두 `예`여야 한다.

1. 비어 있을 때 이 영역의 목적과 다음 행동이 보이는가?
2. 처리 중에도 사용자의 입력과 이전 결과가 남아 있는가?
3. 실패 위치와 재시도 행동이 같은 맥락에 있는가?
4. disabled 행동에 이유가 보이는가?
5. 확정값과 AI 제안을 색상 없이 구분할 수 있는가?
6. 행동 완료 후 다음 포커스가 예측 가능한가?

## 접근성 검수

- 키보드만으로 로그인 → 새 프로젝트 → 질문 답변 → 제안 승인 → 문서 이동 → 다운로드 → 로그아웃을 완료한다.
- 화면 확대 200%에서 주요 행동과 콘텐츠가 손실되지 않는다.
- landmark와 heading outline이 부분 화면의 위계를 반영한다.
- focus indicator가 `--color-border-focus`와 충분한 시각 차이를 가진다.
- live region이 저장, Agent 완료와 새 제안을 중복 낭독하지 않는다.
- reduced motion에서 Drawer와 상태 전환이 멀미를 유발하는 이동 없이 동작한다.

## 완료 게이트

개별 UIR UI PR은 다음 조건을 모두 통과해야 `done`이다.

- 변경 화면의 1440×900·390×844와 영향을 받은 상태 캡처가 작업 기록에 연결됨
- 같은 viewport·상태의 기준 이미지/렌더 화면 쌍과 주요 anchor의 px·% 차이가 기록되고, 설명되지 않은 실질 차이가 없음
- Playwright Chromium 시각·행동 검증 완료. Agent Browser를 사용할 수 있으면 같은 흐름을 검증하고, 사용할 수 없으면 도구 목록·실행 파일 확인 결과를 남긴다.
- 직접 영향받은 중간 viewport의 레이아웃 전환을 확인함
- 키보드와 focus transition 표 검증 완료
- 사용한 `docs/blueprint-design/` 주 이미지, 필요한 `docs/template/` fallback과 반영한 패턴 기록
- raw visual value와 중복 primitive 검사 통과
- P0/P1 UI 결함 없음
- 알려진 차이는 의도, 영향과 후속 작업을 명시

후속 QLT-PR-01은 개별 PR의 병합 이후 위 표의 전체 화면·상태를 5개 기준 viewport에서 통합 감사한다. 이 감사는 앞선 UIR UI PR의 완료 조건이 아니다.

## 실패 판정 예시

- 정상 화면 캡처만 있고 오류·빈 상태가 없으면 실패다.
- 시안과 같은 viewport에서 비교하지 않았거나 설명되지 않은 실질적인 배치 차이가 남으면 실패다.
- 모바일에서 DOM 순서가 시각 순서와 달라 키보드 이동이 꼬이면 실패다.
- 화면 캡처와 비슷하게 보이더라도 semantic HTML, 키보드 동작, responsive behavior가 누락되면 실패다.
- 화면이 맞더라도 저장 실패 후 입력이 사라지면 실패다.
- 숨긴 Drawer에 Tab으로 진입할 수 있으면 실패다.
