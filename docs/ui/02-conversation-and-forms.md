# 대화 작업 공간과 선택 입력

제품 대화 계약은 [대화·결정 프로세스](../product/04-conversation-process.md), 상태·schema 규칙은 [turn 처리 계약](../process/03-question-and-answer-decisions.md)을 따른다. 주 시안은 [대화 캔버스](../blueprint-design/README.md)다. 템플릿 이미지는 주 시안에 없는 빈 상태·오류 상태에만 참고한다.

## 부분 화면

| ID | 영역 | 사용자 목표 |
| --- | --- | --- |
| `UI-CONV-001` | 단계 헤더 | 현재 프로젝트와 대화 단계를 확인 |
| `UI-CONV-002` | 대화 기록 | 사용자와 Agent가 이어온 turn, 응답, 제안 원문과 근거 확인 |
| `UI-CONV-003` | 자유 입력 composer | 어느 시점에서든 설명·정정·추가를 입력하고 자료 첨부 |
| `UI-CONV-004` | 처리 상태 | 실제 AI 작업·저장 상태와 복구 행동 확인 |
| `UI-CONV-005` | 선택 응답 block | 필요한 맥락형 질문·선택 카드에 접근 |
| `UI-CONV-006` | 결정 요약 | 확정 내용·남은 결정을 찾아 출처와 편집 행동으로 이동 |
| `UI-CONV-007` | 결과 보기 | 확정 내용의 그룹·읽기 전용 도식 또는 텍스트 요약 확인 |

## 좌우 구조

```text
프로젝트 제목 + 실제 5단계 위치
┌─ 왼쪽: 대화 흐름과 주 행동 ──────────────────┬─ 오른쪽: 결정 요약 ──────┐
│ 이전 대화·사용자 원문·Agent 응답              │ 확정 내용                │
│ 선택적 질문/선택 카드 또는 제안 검토           │ 남은 결정                │
│ 실제 처리 상태·오류 복구                       │ 제외 이력(필요할 때)     │
│                                             │ 선택한 항목의 출처/행동  │
└───────────────────────────────────────────────┴──────────────────────────┘
┌────────────────────── 자유 입력 + 첨부 + 전송: 두 열 전체 하단에 고정 ──────────────────────┐
```

주 시안에서 대화가 주 영역을 차지하고 `확정 내용`과 `남은 결정`은 보조 요약 영역에 둔다. 데스크톱 composer는 두 열 아래 전체 작업 영역을 가로질러 고정하고, 우측 여백은 34px로 둔다. 요약 패널을 끝까지 스크롤했을 때 마지막 항목이 composer와 겹치지 않게 여백을 확보한다. 오른쪽에는 현재 aggregate에서 확인한 실제 값만 표시한다. 선택한 결정은 source turn, 설계 항목, 상태와 다음 행동을 확인할 수 있고 해당 위치로 이동한다. 단순 thread compaction summary를 실시간 결정 source로 사용하지 않는다.

화면의 단계 이동은 실제 프로젝트 상태와 route에 연결한다. 대화 화면에서 별도 편집기를 가장하지 않는다. 제안 검토가 필요한 경우 기존 proposal stage와 transaction으로 연결한다. 기존 5단계(대화→제안 검토→설계→요구사항 명세→PRD)와 문서 gate를 유지한다.

## 대화 메시지

- Agent는 자연어 응답을 짧게 이어가고, 확인된 사실·추론·제안을 표현에서 구분한다.
- 사용자 메시지는 원문을 보존하고, 첨부 자료는 앱이 허용한 발췌와 file label만 연결한다.
- 제안 요약은 대상·변경 전후·이유·근거·영향과 개별 검토 행동을 제공한다.
- 한 응답의 주 행동은 하나로 유지한다. 질문, recommendation, proposal review를 서로 합쳐 의미를 흐리지 않는다.
- 연속 Agent 메시지는 한 그룹으로 읽되, 각 출처와 동작 가능한 요소를 잃지 않는다.
- 진행 상황은 실제 `GenerationJob`/저장 상태로 표현한다. AI가 보낸 임의 완료율은 사용하지 않는다.

## 맥락형 선택 카드

선택 카드는 대화 turn에 필요할 때만 나타나며 고정 질문 목록을 대신 완료하게 하지 않는다. 자유 입력 composer는 항상 사용 가능하다.

| 입력 성격 | 사용 가능한 표현 |
| --- | --- |
| 하나 선택 | `Radio` 또는 의미가 명확한 2개 버튼 |
| 여러 항목 선택 | 키보드 접근 가능한 `Checkbox`/`MultiSelect` |
| 설명·수정 입력 | `Textarea`와 직접 입력 |
| 수치·범위·순위 | 기존 semantic 입력 control과 연결된 오류 |
| 확인·보류 | 동작 의미를 텍스트로 구분한 명시적 선택 |

- 한 대화 응답의 후속 질문은 최대 1개다. 질문 없이 끝나는 응답도 정상이다.
- option은 대화 맥락과 확정 설계에 근거하고 직접 입력으로 보완할 수 있다.
- 선택만으로 제출, 승인 또는 확정되지 않는다.
- 화면은 strict schema를 통과한 allowlisted renderer 타입만 사용한다: `single_choice`, `multiple_choice`, `free_text`, `number`, `range`, `rank`, `confirm`. 이 component registry는 렌더 타입만 고정한다. 질문과 선택지 콘텐츠는 현재 대화·확정 설계·허용된 근거에 맞춰 생성하며 predefined recommendation/question content를 재사용하지 않는다.
- 모델이 반환할 수 있는 것은 registry 타입과 제한된 표시 데이터뿐이다. HTML, React, 코드, 스타일, 임의 component/action/ID는 거부한다. schema 실패는 block을 표시하거나 저장하지 않고, 원문을 보존해 재시도한다.
- 명시적 추천 요청은 근거가 충분할 때 11개의 후보를 보여준다. 후보는 초기 선택 상태가 아니며 사용자가 선택한 안만 제안 검토에 연결한다. 정보가 모자라면 11개를 꾸미지 않고 확인 질문을 한다.
- 11개 후보 목록은 최대 높이와 내부 키보드 스크롤을 갖추고, 모바일에서는 자연스럽게 세로로 읽는다. 현재 선택과 전체 수를 텍스트로 표시한다.

## 추천 결과와 도식 결과

추천 후보는 확정 데이터와 구분해 제안으로 보여준다. 후보별로 근거, 기대 효과, trade-off, 가정을 읽을 수 있어야 한다. 선택된 후보는 pending proposal이 되며, 사용자가 기존 승인 transaction을 완료하기 전에는 우측 `확정 내용`이나 확정 도식에 반영하지 않는다.

대화 중 오른쪽 패널은 실제 `확정 내용`과 `남은 결정`을 나눈다. 설계 단계의 그룹 카드와 도식은 확정 항목으로 계산한 읽기 전용 projection이다. 사용자는 설계 항목 상세의 `관련 확정 결정`에서 다른 확정 항목을 명시적으로 연결하거나 해제할 수 있다. 이 행동은 양쪽 `relatedItemIds`와 설계 revision을 한 저장 transaction에서 함께 갱신하며, AI는 관계를 만들지 않는다. 각 도식 노드는 원본 결정과 근거로 이동한다. 관계 근거가 부족하면 도식 대신 같은 내용을 텍스트 목록으로 제공하고, 제안·미정 내용을 확정 관계처럼 그리지 않는다. 도식 자체에서 관계를 편집하는 범용 canvas는 추가하지 않는다.

## 결정 패널 상태

| 상태 | 표시 | 행동 |
| --- | --- | --- |
| 확정 | 확정값, 원본 영역, source, revision | 대화 출처 보기, 설계 상세/수정 |
| 제안 | 제안 badge, before/after, 근거 | 제안 검토로 이동 |
| 보류·미정 | unresolved 이유와 출처 | 대화에서 다시 결정 |
| 충돌·재검토 | 기존값·새 제안·영향 | 비교·해결 |
| 없음 | "아직 확정된 내용이 없습니다"와 실제 다음 행동 | 대화 계속 |
| 저장/AI 실패 | 오류 원인 범주, 확정 상태 유지 | 재시도 또는 검토 |

요약 갱신은 승인 transaction 성공 후 같은 aggregate revision에서 수행한다. 저장 중에는 이전 확정값을 유지하고, 실패 때 성공처럼 표시하지 않는다.

## Composer와 접근성

- `Textarea`, 이름이 분명한 첨부 버튼, 전송 버튼으로 구성한다. 승인되지 않은 시안 마이크는 추가하지 않는다.
- Enter는 줄바꿈, `Ctrl/Cmd+Enter`는 전송이며 안내를 제공한다.
- 전송 중 작성 중 원문을 보존하고 중복 요청을 막는다.
- 질문 카드가 없어도 composer는 대화 작업 영역의 기본 행동이다.
- 오류는 관련 입력·작업에 연결된 live status/alert로 제공하며, 실패 원문을 잃지 않는다.
- 패널 내 숨긴 내용은 접근성 트리와 키보드 순서에서도 숨긴다. Drawer를 닫으면 선택한 결정·대화 위치로 focus를 돌린다.

## 반응형

- 1280px 이상에서는 대화 왼쪽, 결정 요약 오른쪽의 주 시안 위계를 유지한다.
- 좁은 화면에서는 대화를 먼저 읽고 요약은 대화 뒤 또는 명시적 toggle로 연다.
- 390px에서 composer와 OS safe area가 마지막 메시지·선택 카드·키보드 focus를 가리지 않는다.
- 오른쪽 항목 또는 11개 후보 목록은 수평으로 잘리지 않는다. 긴 내용을 내부 스크롤 또는 다음 섹션으로 제공한다.

## 수용 기준

- 사용자는 catalog 질문에 답하지 않고도 첫 아이디어부터 자유 대화를 진행할 수 있다.
- 대화 중 선택 카드가 나타나지 않아도 모든 primary 기능에 접근할 수 있다.
- 선택 카드 내용은 현재 대화에서 생성되고 allowlisted/schema-validated renderer로만 표시된다. predefined 질문·추천 콘텐츠에 의존하지 않는다.
- proposal 승인 전에는 우측 확정 내용·도식이 바뀌지 않고 저장 후에는 source와 같은 revision으로 갱신된다.
- 오른쪽 각 결정에서 대화 근거/설계 상세로 이동하고 다시 composer로 돌아올 수 있다.
- 명시적 추천 요청에서 근거 있는 후보 11개, 부족한 맥락 확인, 후보 선택→proposal→승인의 연결이 분리되어 검증된다.
- 모바일·키보드·screen reader에서 대화와 결정 패널을 오갈 수 있고 focus/입력 원문이 보존된다.
