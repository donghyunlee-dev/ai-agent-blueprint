# 대화·설계 발견

주 시안과 좌우 배치는 [Blueprint redesign map](../../blueprint-design/README.md)의 대화 캔버스다. UI behavior 정본은 [대화와 선택 입력](../02-conversation-and-forms.md), 제품 대화 정본은 [대화·결정 프로세스](../../product/04-conversation-process.md)다. 템플릿 캡처는 새로운 디자인에 없는 대화 생성/빈/오류 상세 상태만 참고한다.

## F-CONVERSATION — 새 프로젝트 첫 turn

```text
공통 frame: 프로젝트 이름 · 저장 상태 · 실제 단계
┌─ 왼쪽: 연속 대화 ───────────────────────────┬─ 오른쪽: 요약 ─────────────┐
│ 사용자의 첫 제품 설명                        │ 확정 내용                  │
│ 최초 AI data-use 안내는 전송 전에 확인         │ 아직 확정된 내용 없음       │
│ 응답 대기·취소·오류                            │ 남은 결정                  │
│ 자유 composer + 지원 첨부 + 전송              │ 비어 있음을 명확히 표시     │
└──────────────────────────────────────────────┴──────────────────────────┘
```

최초 AI data-use 동의는 첫 provider 전송 전에 blocking consent로 받는다. 이미 동의한 프로젝트에 반복 동의 배너를 표시하지 않는다. 기본 empty summary는 오류처럼 보이지 않으며, 임의의 예시 프로젝트나 결정 데이터를 표시하지 않는다.

## F-TURN — 이어지는 대화

각 사용자 메시지는 원문 그대로 보존한다. Agent는 과거 대화·현재 확정 설계·허용된 자료를 참조해 자연스럽게 응답하고, 추가 확인이 유용한 경우만 질문 또는 choice card 하나를 맥락에서 생성해 덧붙인다. 고정 `QUESTION_CATALOG`는 현행 구현 사실이며 목표 질문/추천 source가 아니다. 앱은 strict schema로 검증한 allowlisted component type만 렌더링하며 모델은 HTML/React/code/action을 반환할 수 없다. 자유 입력은 선택 카드 전후, 제안 검토 중에도 사용할 수 있다.

```text
사용자: 사내 회의실을 예약하고 운영할 서비스를 만들고 싶어요.
Agent: 회의실 예약과 운영을 한곳에서 관리하려는 것으로 이해했어요.
       회의실 현황 조회, 예약, 운영 관리까지 후보로 정리했어요.
       [사용자 승인/수정/거절이 필요한 제안은 pending으로 표시]
       주요 사용자를 먼저 확인하면 기능과 권한을 구체화할 수 있어요.
       [선택 카드가 유용할 때만 표시] [자유 입력도 가능]
```

질문은 이전에 결정한 사실을 반복하지 않고, 사용자의 입력 내용만으로 이미 알 수 있는 것을 묻지 않는다. 대화가 명확하면 질문 없이 응답할 수 있다.

## F-DECISION-SUMMARY — 오른쪽 확정·미결정

```text
요약
확정 내용
  • 사용자가 승인한 값 · 출처 보기
  • 같은 revision의 결정 항목

남은 결정
  • 검토 대기 제안 · 제안 검토로 이동
  • 보류/충돌 · 이유와 해결 행동
```

제안이 사용자 승인 전이면 `확정 내용`에 보이지 않는다. 항목을 선택하면 상태, value, source turn/자료, 관련 설계 영역과 안전한 다음 행동을 보여준다. 승인 command가 성공한 후에만 오른쪽 확정값을 갱신한다. compaction summary는 실시간 panel source가 아니다.

## F-RECOMMENDATION — 명시적 11개 추천 요청

사용자가 대화 중 직접 추천을 요청하면, 현재 맥락이 충분한 경우에 한해 11개의 서로 다른 후보를 제안 결과로 보여준다. 11개 후보는 초기 선택되어 있지 않으며 후보별로 근거·맞는 이유·trade-off를 표시한다. 사용자는 후보 중 필요한 것만 선택해 pending proposal로 만든 후 기존 승인 흐름을 밟는다.

맥락으로 11개의 타당한 후보를 뒷받침할 수 없다면 후보를 채우지 않는다. Agent가 필요한 사실을 자유 대화로 확인한 뒤 다시 추천할 수 있게 안내한다. 추천 요청이 아닌 보통 turn에서는 11개 목록을 강제로 표시하지 않는다.

## F-DIAGRAM — 설계 결과

요약이나 설계 단계에서 확정된 결정을 그룹 카드로 스캔하거나, 근거가 충분한 경우 읽기 전용 관계 도식을 확인한다. 도식 항목을 고르면 원본 결정과 대화 출처를 연다. 미확정·미정·충돌은 별도 상태로 보이고 확정 관계에 섞이지 않는다. 확정 관계가 충분하지 않으면 동일 데이터를 텍스트 목록으로 제공한다.

## 실패·복구 상태

| 상태 | 왼쪽 대화 | 오른쪽 요약 |
| --- | --- | --- |
| AI 대기 | 실제 작업과 취소 행동 표시 | 기존 저장 상태 유지 |
| AI 오류 / schema 거절 | 원문 보존, 원인 범주와 재시도 | 변경 없음 |
| 요청 결과 unknown | 요청 lifecycle에 따른 확인/잠금 설명 | 현재 저장된 aggregate 그대로 |
| 저장 실패 | 변경을 확정했다고 표현하지 않음 | 이전 확정 revision 유지, 저장 재시도 제공 |
| 충돌/stale | source와 변경 전후 비교로 이동 | 기존값 유지, 해결 필요 표시 |
| 새로고침 후 복구 | 저장된 messages/job과 입력 복원 | 현재 aggregate로 다시 계산 |

## 모바일과 키보드

- 대화와 composer를 먼저 읽고 사용할 수 있다. 요약은 아래에 이어지거나 명시적 토글로 연다.
- 보조 패널 열기/닫기는 키보드로 가능하고 닫은 후 trigger로 focus를 반환한다.
- 질문 card가 없는 상태에서도 composer와 전송 행동은 유지된다.
- OS safe area, 가상 키보드와 긴 제안 목록은 마지막 내용과 현재 focus를 가리지 않는다.
- loading/empty/error 상태는 색상만으로 전달하지 않고 텍스트와 행동을 함께 둔다.

## 수용 기준

- 첫 입력→AI 대화 응답→제안 검토→사용자 승인→우측 확정 결정 갱신을 한 fixture 흐름에서 검증한다.
- 추천 후보는 정확히 11개이며, 선택·제안·승인은 별도 단계이고 미승인 후보가 확정 요약에 나타나지 않는다.
- 11개를 근거로 만들기 어려운 경우는 후속 질문이 나오고 후보를 임의로 채우지 않는다.
- right-side decision/source navigation은 same-revision aggregate를 가리킨다.
- 오류, cancel, unknown, 저장 실패, refresh와 mobile/keyboard 경계에서 입력·확정 상태가 보존된다.
