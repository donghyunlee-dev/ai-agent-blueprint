# 3단계 — 제안과 구조화 설계

## 목표와 사용자 결과

한 답변이나 자료에서 발견한 여러 설계 항목을 사용자가 개별 검토하고, 승인한 내용만 공통 설계에 누적한다. 사용자는 대화 중에도 무엇이 확정·미정·재검토·충돌 상태인지 확인한다.

## 연결 기준

- 화면 설계: [설계 보드와 Inspector](../ui/03-design-board-and-inspector.md), [제안·충돌 청사진](../ui/screens/03-proposal-and-conflict.md), [설계·준비 상태 청사진](../ui/screens/04-design-and-readiness.md)

- 요구사항: `PROP-001`~`PROP-004`, `DES-001`~`DES-003`
- 결정: `DEC-002`, `DEC-003`, `DEC-004`, `DEC-006`, `DEC-012`
- 선행 조건: 2단계 turn API, 질문 엔진과 폼 완료

## 상태 모델

```text
Agent payload
→ pending proposal
→ accepted | edited_and_accepted | rejected | superseded
→ confirmed design item
→ dependency check
→ current | review_required | conflict
```

## 작업 단위

### DSG-301 제안 정규화

구현:

- 하나의 제안이 하나의 target과 operation만 갖도록 응답을 분리한다.
- create, update, delete와 before/after, rationale, evidence를 검증한다.
- 같은 requestId와 target 조합의 중복을 제거한다.

성공 조건:

- 사용자·기능·제약이 한 답변에 있으면 각각의 카드로 나온다.
- 근거 없는 Agent 추론은 `agent_inference`로 표시되고 확정되지 않는다.
- 대상이 존재하지 않는 update/delete는 거절된다.

### DSG-302 제안 검토 UI

카드 표시:

- 변경 유형과 설계 영역
- 제안 제목과 값
- 기존 값이 있으면 전후 비교
- 이유와 근거 발췌
- 영향받는 항목과 문서
- `거절`, `수정 후 승인`, `승인`

성공 조건:

- 일부 제안만 처리할 수 있다.
- 현재 질문 관련 미처리 수를 표시한다.
- 관련 제안이 남아 있으면 다음 시스템 질문을 잠근다.
- 자유 대화 입력은 계속 사용할 수 있다.

### DSG-303 승인과 수정

구현:

- 승인 시 현재 값과 proposal before를 다시 비교한다.
- 수정 후 승인은 수정한 값만 confirmed item으로 저장한다.
- 삭제 승인은 항목을 즉시 제거하지 않고 `archivedAt`을 기록한다.
- 상태 변경과 activity를 하나의 저장 transaction으로 처리한다.

성공 조건:

- 승인 전 설계·문서에 제안값이 확정값처럼 나타나지 않는다.
- 저장 실패 시 proposal과 기존 confirmed item을 유지한다.
- 같은 승인을 반복 실행해도 revision이 한 번만 증가한다.

### DSG-304 충돌 해결

진입 조건:

- proposal의 before와 현재 confirmed 값이 다름
- 새 제안이 기존 확정 의미와 양립할 수 없음

화면:

- 기존 값과 근거
- 새 값과 근거
- 영향받는 요구사항·문서
- `기존 유지`, `새 값 선택`, `수정해서 적용`

성공 조건:

- 해결 전 기존 확정 값을 유지한다.
- 해결 결과와 선택 이유를 activity에 기록한다.
- 충돌이 하나라도 남으면 문서 생성 상태가 `ready`가 되지 않는다.

### DSG-305 의존 항목 재검토

구현:

- 선행 결정이 바뀌면 종속 항목을 삭제하지 않고 `review_required`로 전환한다.
- 영향 관계와 재질문 후보를 생성한다.

성공 조건:

- 인증 불필요로 변경하면 기존 로그인 방식이 사라지지 않고 재검토로 표시된다.
- 사용자는 어떤 선행 변경 때문에 재검토가 필요한지 확인할 수 있다.
- 재확정하기 전 문서에는 현재 상태가 명시된다.

### DSG-306 설계 보드와 준비 상태

영역:

- 제품 정의
- 문제와 목표
- 사용자와 시나리오
- 범위와 제외 범위
- 핵심 기능과 수용 기준
- 데이터·권한·외부 연동
- 운영·보안·제약
- 성공 기준과 위험

표시 상태:

- 확정
- 제안
- 미정
- 재검토
- 충돌

성공 조건:

- 숫자 준비도를 표시하지 않는다.
- `부족`, `작업 가능`, `준비 완료`와 영역별 상태를 표시한다.
- 부족 영역을 선택하면 관련 질문 또는 항목으로 이동한다.
- 색상과 함께 아이콘과 텍스트를 사용한다.

### DSG-307 일괄 처리

구현:

- 충돌과 검증 오류가 없는 제안만 일괄 승인 대상으로 계산한다.
- 실행 전 승인·제외 수와 제외 이유를 표시한다.

성공 조건:

- 충돌 제안은 일괄 처리로 확정되지 않는다.
- 일부 저장 실패가 발생하면 전체 transaction을 되돌린다.

## 필수 테스트

1. 한 답변에서 복수 제안 분리
2. 개별 승인·수정·거절 조합
3. stale proposal 충돌 전환
4. 기존/신규/수정 충돌 해결
5. 선행 결정 변경에 따른 review_required
6. 미정은 허용하지만 충돌은 문서 생성을 차단
7. 일괄 승인 대상 계산과 atomic rollback
8. 설계 보드 키보드 탐색과 상태 읽기
9. 데스크톱 상세 패널과 모바일 Drawer

## 완료 증거

- proposal 상태 전이 단위 테스트
- 충돌·종속성 fixture
- 설계 보드 전체 상태 캡처
- 모바일 Drawer 포커스 진입·복귀 기록
- readiness gate 테스트

## 단계 종료 조건

사용자 승인으로만 confirmed 상태가 만들어지고, 충돌·재검토·미정이 구분되며, 준비 상태가 확정 설계에서 결정되어야 한다.
